Engineering rulebook

The rules every change to Vervoro must keep, for people and for coding agents. Each rule is a short summary of a decision that a record makes, and links to it. The record wins: if a rule here and its record disagree, follow the record and fix this page. Nothing here decides anything new.

Load this page with any task. Load the linked record before changing the area it covers. A rule binds whatever its record's status: while a record is Proposed its rules may still change, but only by changing the record first. Parts a record marks Later are built only when their trigger arrives. The words used here are defined in the map and glossary.

Which record owns which rule. Each of these rules is stated in full in one place. Every other record links there instead of restating it; a copy that drifts from its owner is fixed to a link.

1. When in doubt, stop

  1. Never guess when correctness is uncertain. A wrong company, an unknown write, an incomplete order read, an unreachable control database or a broken stock rule stops the work, records what is uncertain and settles it. It never carries on with a best guess. ADR-001, ADR-004, ADR-008
  2. Cross-company exposure and corrupted stock are the worst failures. A sign of cross-company exposure pages the operator and closes the database's egress (on control, every cell's). A stock difference found by the nightly check alerts the operator and the company's managers and holds raises on the affected listings, while decreases still go. ADR-001, ADR-006

2. Companies and databases

  1. One control database and many cells; no schema per company. Control holds the platform's own data (companies and where they live, memberships, logins and Better Auth's sign-in tables, operators, plans, quotas, the sync epoch, the erasure register), never company business data. A cell holds many companies in shared tables. Control and every cell are each a Neon project of their own; a Neon branch is only a short-lived copy, never holds live data, and is deleted within 24 hours. A dedicated database (Later) is a cell with one company, using the same schema and code path. ADR-001, SPEC 7
  2. Every transaction enters exactly one company first. Its first statement is app.enter_company (at sign-up, app.open_tenant), which raises unless this database holds that company and it is open. An unset company is an error, never zero rows. No autocommit for company work. ADR-001
  3. Isolation is enforced by the database, not by remembering a filter. This rule, rule 4, rule 7's commit check and rule 9's routing are the security boundary; rule 6 is defence in depth. Every tenant table has company_id first in every key, composite foreign keys, and forced row-level security. The runtime role logs in as itself with NOBYPASSRLS, and the owner role migrates from the CI migration job only. No role is ever created in the Neon console; Neon's own internal roles (today neon_service) are the one exception, named exactly in the lint and the audit, alerted on when Neon's list changes, and never used by Vervoro. ADR-001, SPEC 3
  4. Modules never write SQL. They declare tables through tenantTable() and query through the typed query builder the data layer gives them, which has no raw-SQL helper and calls only allow-listed functions; upserts go through conflict(). A run-time query check refuses, failing closed, any raw-SQL node, any function off the allow-list and any table outside the module's set. Raw SQL lives only in the kernel's data layer and in migrations. A query the builder cannot express gets a reviewed view or builder extension, never raw SQL. There are no serial or identity columns; ids are uuidv7. ADR-001
  5. Only the data layer sets the company. Module queries cannot set or read the company setting, control transactions or change the schema, and the data layer checks the company is unchanged before every commit. That commit check is part of the boundary, because any SQL inside a transaction could change the company setting, which row-level security does not fence. Only two tables, due and buyer_ref, are read across companies, and only through two allow-listed functions that return ids and times. ADR-001
  6. Every cache key includes the company id, and Hyperdrive query caching stays off. Logs carry ids, never field values, and invocation logs are off. Queue messages, Durable Objects and live updates carry ids and statuses only, in the EU jurisdiction. No Worker binds a key-value store, SQL database or analytics store. ADR-001, ADR-000
  7. A company's database is found through routing, never configured. forCompany(id) reads company.database_id from control. Adding a company needs no new database and no deploy; adding a cell does. When control cannot be reached, work waits: no session, route, pool token or sync epoch is trusted from a cache, and nothing is sent to a marketplace, a decrease included. ADR-001
  8. No transaction spans two databases. A write that touches a cell and control writes the company side first, with an outbox note, then control, and is safe to repeat. ADR-001
  9. Company-level operations use the one slice operation, under the lifecycle role, never the owner, in batches: export, restore and erase, and moves and dedicated placement when they are built (Later). ADR-001
  10. Schema changes expand, migrate, then contract, and run on every database before new code goes live. A change first adds in a backward-compatible form; code that understands both shapes deploys and the data is moved; a later release removes the old shape only after the rollback window, at least 24 hours and one successful nightly cycle. A destructive change never ships in the same release that first depends on the new schema. A migration is never rolled back, and one already merged is never edited. Production is migrated and deployed only by the CI job. Until launch, staging may be deployed from the owner's laptop by the same script, with staging-only credentials and synthetic data, and it keeps production's roles, row-level security, migration order and EU placement. ADR-000, ADR-001
  11. Append-only tables say so where they are declared. The runtime role cannot update, delete or truncate them. Their rows leave only through the slice operation, by a whole month detached after the archiver verified it, or, for outbox notes every handler has received, deleted 30 days after the last receipt by the lifecycle role. Logs and send records are deleted when their time ends, never archived. ADR-001, ADR-002

3. Modules and the foundation

  1. One main application deployable, plus the separate sign-in Worker; every feature is a module. The sign-in Worker is kept apart on purpose (ADR-013). A module owns its tables, prefixed with its id, and talks to other modules only through their typed ports and events. A foreign key may point only into a core module's tables. ADR-000, SPEC 2
  2. Only Inventory changes stock, only Orders changes order status, and only Stock sync works out the figure a listing should show. The foundation is six always-on core modules, each the only writer of its own data; Listings alone changes links. They share one transaction where they must. Stock sync works out a listing's figure from each committed stock change, through the outbox, and never replaces a newer figure with an older one (ADR-008 owns this). Other modules call their ports, and calls always point toward the core. ADR-000, SPEC 4
  3. Expected failures are typed Result values. No silent catches. ADR-000
  4. Events are written with the change. An outbox note goes in the same transaction, is delivered after commit, and is handled once, with a receipt per handler. ADR-001
  5. The client is not a security boundary, and no screen waits for a marketplace. It is built only from the UI package and styled only from the token package; every word comes from the catalogue, and every interactive element has a test id. A request never calls a marketplace: screens show stored copies with their age, and slow work runs in the background. A tap that changes something shows sending, done or not sure, shows done only on the server's answer, and retries with the same key. ADR-000 SPEC 10, SPEC 12, SPEC 13

4. Stock

  1. Only a ledger insert changes a balance or a reservation. The ledger is append-only, and every entry has a reason, an actor and a source. ADR-006
  2. Stock never goes below zero and is never quietly set to zero. Reserved plus held never exceeds on hand. Only sellable ever reaches a listing. ADR-006
  3. Every stock command takes the company's lock first and is safe to repeat. A command carries a key, and a repeat with the same key returns the first answer and moves nothing. An order import carries no key: it is safe to repeat by its targets, so the same state moves nothing and a newer one moves only the difference. ADR-006
  4. An order reserves when it is imported, in the same transaction. Each reservation names a batch, never a spot. A bundle reserves its components in whole sets. A shortage reserves what exists and records the rest; Vervoro never cancels the order. ADR-006
  5. Stock leaves only when a shipment is confirmed, or when the marketplace reports a line shipped outside Vervoro. One shipment carries the whole order and deducts exactly what was packed for it, once. A cancellation request releases nothing; only a confirmed cancellation does. ADR-014, ADR-006, ADR-007
  6. A use-by batch is never reserved, packed or dispatched on or after its date, by any route, with no override. An undated batch of a use-by product counts as past its date until its date is entered. ADR-006
  7. Every quantity is a whole number of base units of one product, and weights and sizes are stored in whole grams and millimetres. Other units are converted only on entry and display. ADR-003 SPEC 2.1, SPEC 15
  8. A charge that is not stock is a charge line, never a product. It never reserves or moves stock; a marketplace listing that is not stock is marked so, never linked. ADR-003 SPEC 1.1

5. Marketplaces

  1. Nothing reaches a marketplace or a supplier except through the egress gate. Every outbound effect is recorded in the transaction with an idempotency key and sent only after commit. For every send the gate reads the account's mode from the database: live sends, decrease-only sends only decreases, and shadow and every other mode only record. ADR-000
  2. Nothing leaves Vervoro during a database transaction. No marketplace or other outside call runs inside one, so a company's lock is held only for database work, and Postgres's transaction timeout ends a transaction that runs too long. ADR-000, ADR-001, ADR-006
  3. A connector only translates. It has no network access, credentials, clock or database. Channels, the host, owns credentials, HTTP, retries, rate limits, shared allowances, notice checks and the sending half of the egress gate. Core code knows marketplace concepts such as listings, links and FBA, but not marketplace protocols. ADR-004
  4. Orders come in by notice. A notice is checked before any database read, queued as ids only, and is a hint: the order is fetched and imported. The scheduled read is only the backup, and only a complete read moves the order watermark. Amazon's notices reach the same path through an AWS bridge. ADR-004, ADR-007
  5. Each marketplace order is imported once, keyed by account and marketplace order id. A fetch older than the stored one changes nothing. Cancelled and shipped-outside units only rise, and a line keeps the listing it reserved with; a fetch that seems to undo either holds the order. A label bought on the marketplace is Vervoro's own shipment: it closes when the order is packed here, deducts what was packed, and sends no dispatch notice (ADR-007 SPEC 17, ADR-014 SPEC 4). An order that cannot be imported becomes a problem row; it is never dropped. ADR-007
  6. Vervoro never sends a cancellation. The seller cancels on the marketplace, and only a confirmed cancellation releases stock. A buyer's request holds the order; a hold keeps the reservation, sends nothing, and stops picking, packing and dispatch. ADR-007, SPEC 11
  7. A timeout is unknown, not failed. An unknown write is settled before anything else is sent to that listing. Read-back is the default; a connector may instead send again the absolute figure Vervoro wants now only when the write sets a value (never adds to one), repeating it cannot compound, and its record names the exception (eBay's Trading API). ADR-004, ADR-004.1
  8. Figures go only to linked listings. Nothing but its quantity and the offers the seller asks for is ever written to a listing, and Vervoro never changes a seller's marketplace settings. ADR-005, ADR-004.1
  9. No raise leaves before a complete order read covers the moment it became due. A raise also waits two minutes for clocks. Near zero, every change is sent; above that, a figure is sent once it is 20 away from what the channel shows, only where a channel's own sales are known to come out of Vervoro's figure; everywhere else every change is sent. A held raise never holds a decrease. ADR-008, ADR-005 SPEC 11.3
  10. One writer per listing, one open write at a time, and every write confirmed. Amazon's accepted is not applied. ADR-008
  11. Every account starts in shadow, and returns to shadow after a restore, a reconnect or a closed company's reopening. Going live first needs a payment method, the account's stop choice and a stock contact. No account on a marketplace goes live until shadow there passes its launch gates (lost notices, detection delay, unreserved orders). A restore raises the company's sync epoch, so no earlier write is mistaken for a later one, and restored sends are unknown, never resent. ADR-004, ADR-008, ADR-012, ADR-001
  12. Every stop asks one question: leave the figures, or send zero. It is asked at going live and kept; a zero is confirmed applied before the mode changes, and Vervoro never sends zero unasked. A company closed for non-payment carries out each answer, then its accounts are decrease-only until erasure: orders import and reserve, and no figure is ever raised. ADR-008, ADR-012
  13. Testing is layered, and development uses simulators, never a real marketplace. Pure logic runs as fast unit tests with no database; the database, row-level security, locking, routing and triggers run on real Postgres, the production major version; marketplace behaviour runs on the simulators; critical flows run end to end. The in-process database only runs the app on a laptop, and no test depends on it. No simulator code reaches production. A test that protects accepted behaviour is removed or weakened only together with an accepted change to that behaviour or its SPEC. ADR-000 SPEC 15

6. People and buyer data

  1. Every request is checked on the server against the person's role, warehouse scope and status in that company, and its membership not paused, read in the same transaction as the work. Account changes (people, roles, scope, connections, going live, an export with buyer data, an operator's buyer-data access, closing, billing) also need a session started in the last 5 minutes. ADR-010 SPEC 5
  2. Operators have no standing access. To look inside a company an operator uses a read-only grant with a written reason and an end time at most 8 hours away, which the seller sees and can end; buyer data stays masked unless an Owner or Admin switches it on. Repairs run as recorded commands under a system actor, never as the database owner role, and erasure is never an operator command. Developers have no access to production data. ADR-010 SPEC 7
  3. Sign-in is Better Auth inside the sign-in Worker, and nothing else. Only the sign-in Worker runs Better Auth, holds its secret, shows a password field and touches the auth and auth_policy schemas; no other code queries or writes Better Auth's tables. Nobody writes passkey, authenticator-code, password-hashing or session code beside it, forks it or patches it. The app asks the sign-in Worker whether a session is live and never records a fresh check itself; its pages and calls are a closed list. ADR-013 SPEC 8
  4. Better Auth says who; ADR-010 says what. The sign-in Worker hands the app a login id and the session's facts; companies, roles, scope, permissions and operator grants are decided only by Access. Better Auth's organisation and access features stay off. ADR-013, ADR-010 SPEC 5
  5. A passkey, or a password with its second factor; never a password alone. Passkeys are the default and need the fingerprint, face or PIN check. Only the methods ADR-013 names are switched on. Better Auth's session is the only one: at most 24 hours for everyone, never extended. Better Auth and its plugins are exact-pinned and upgraded only through a reviewed, committed schema migration and the sign-in tests, never at start-up; no agent changes its setup or schema without the record. ADR-013 SPEC 1, SPEC 5, SPEC 13
  6. Buyer data comes only from the fetched order or a manual order's form, only the fields ADR-009 allows, encrypted per field under the company's key. Until Vervoro prints labels, no recipient name, address or phone is taken from a marketplace, and the destination country and territory are the order's, not buyer data. Every buyer field carries the pii tag, and a build check refuses a column holding buyer data without it. It never goes to control, queues, logs, URLs, caches, emails, client storage or the AI provider. ADR-009, SPEC 4 and SPEC 5
  7. Every view of buyer data is logged. It is anonymised 30 days after delivery, dispatch as the fallback; a cancellation or an ended connection starts the 30 days sooner, a buyer's erasure acts at once, and an anonymised order never stores personal data again. ADR-009, SPEC 7 and SPEC 8
  8. No real buyer data outside production. Tests, fixtures and demos use synthetic buyers. ADR-009, SPEC 15

7. Money and countries

  1. Money always carries its currency, and amounts in different currencies are never added. ADR-000, ADR-003
  2. Country rules live only where the country matters: VAT and invoices, Vervoro's billing, food law, and each marketplace's site. A product has a VAT class, and every line stores the country, class and rate it used; a later rate change never rewrites it. ADR-000, ADR-011 SPEC 6
  3. Nothing that moves orders or stock is ever refused for a billing reason. A plan refuses only switching on a module it does not include. ADR-012 decision 3, SPEC 3
  4. An issued invoice or credit note never changes. One gap-free series per company, numbered in the issuing transaction; a mistake is corrected only by a credit note. Vervoro refuses to issue for an account whose marketplace invoices its orders. ADR-011 decisions 2 and 8, SPEC 5

Writing a rule

How a rule in any record is written, so that building it needs no second ruling. These rules decide nothing new about the product; each points to where its area is owned (owner ruling, 23 October 2026).

W1. Numbers. Every limit names its number, its window and what it counts. Every field a person types names its length. Anything mailed to an address a stranger typed has a daily cap per address (ADR-013 SPEC 7). W2. Retention. Every stored item names how long it is kept, what deletes it (a sweep, a library or the end of its parent) and whether its end is logged. A library that deletes on its own is named, with when it does. A SPEC's data table carries a "Kept until" column, added when the record is next amended (ADR-002 SPEC 2). W3. Mail. Every rule that sends mail names who sends it, the sign-in Worker or the app, each with its own sender and key, through the one provider choice. A send that fails never fails the request; it is logged with codes only (ADR-013 SPEC 8.5). W4. Repeats and claims. Every action that may be repeated names its key, the key's scope (actor, route and request), how long the key is kept and what a repeat is answered. A claim across a boundary returns the same claim on every call, never a second one (ADR-001 SPEC 5, ADR-000 SPEC 12). W5. What an answer reveals. Every call across a boundary, and every page answer, names what it tells the caller. An answer to an address someone typed never shows whether it has a login: not by words, by time taken or by counts (ADR-013 SPEC 7). W6. When a rule is judged. A rule that changes someone's state says when it is judged (at sign-in, on each request, or when something happens) and what it does to sessions and work already running. If it is silent, it applies from the next start, and work that is running carries on. A rule that must end live work says so. W7. Browsers. A screen rule says what the page does where the browser cannot do the thing, or cannot tell whether it can. The server never assumes what a device holds (ADR-000 SPEC 12). W8. Libraries and platforms. A rule that a library or platform carries out names the setting, call or behaviour that does it, checked against the pinned version before the record is Accepted. What cannot be checked is an open item with its fallback (ADR-000 SPEC 16).

Changing a rule

A rule changes only when its record changes. Amend or replace the record first, with the owner's approval, then update this page in the same change.

Small gaps found while building (a silent edge, a number, a way of doing what a rule intends) come as proposed SPEC wording, gathered per record and approved by the owner in one batch, then published as one amendment per record. Such wording may only describe what a rule already intends, or fill a silent edge with the least strict default that matches the other rules; it never relaxes a rule the code broke. An edge case is weighed by how likely it is: one that needs near-impossible timing and that the next action repairs gets one line in its record, not a rule to build (owner ruling, 23 October 2026). Product decisions, and anything that touches isolation, stock, buyer data, the sign-in Worker's closed list or the security log, still come to the owner one by one (owner ruling, 23 October 2026).
