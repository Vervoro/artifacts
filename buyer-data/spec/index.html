1. Who does what

  1. Buyer data writes every buyer field, the eBay buyer hash, label files, privacy requests, the anonymisation of an order and the audit entry for each view. No other module writes them.
  2. Orders hands over the buyer fields of a fetched order through Buyer data's port, in the import's transaction, only for orders the seller ships (ADR-007). Buyer data never takes them from a notice body. Only the fields section 4 marks "at launch".
  3. Other modules read through Buyer data's port, which checks the role and the order's state (section 7) and writes the view entry: Fulfilment for picking, packing and labels (ADR-014); Invoicing for the starting point of a customer block (ADR-011). A recall reads the order's country, not Buyer data (ADR-014).
  4. Whoever buys a label hands the file to Buyer data's port, which encrypts and stores it.
  5. Channels records a marketplace's privacy notice with its due date (ADR-004 SPEC 8) and passes it to Buyer data's port, which opens the company's privacy request.
  6. Access decides the role (ADR-010 SPEC 4); Buyer data decides what that role sees of an order in its current state.

2. Roles and agreements

  1. The seller is the controller. They sell to the buyer, choose the carrier and decide to ship. Vervoro processes buyer data only on the seller's instructions: the product's settings and actions.
  2. Vervoro is the controller only of its own account data (the seller's users, billing, sign-in) and its platform security logs.
  3. The data processing agreement is part of the customer terms, accepted before the first marketplace connection. It covers what UK and EU law ask of a processor contract (ICO): documented instructions; confidentiality; the security measures of this page; sub-processors under general authorisation with 30 days' notice and the right to leave before a change; help with buyers' requests and breaches; deletion at the end, after an export if wanted; audits, through evidence first.
  4. Marketplace terms bind Vervoro directly: Amazon's Data Protection Policy and Acceptable Use Policy as solution provider, eBay's API License Agreement as an independent controller, Shopify's API terms as app developer. Where one is stricter than the agreement, Vervoro follows it, and the agreement says so.
  5. Carriers are the seller's. The seller connects their own carrier accounts; sending an address to buy a label is the seller's instruction.

4. What is kept

Each field only for its purpose, and only from the marketplaces that send it. Until Vervoro prints labels, the recipient's name, address and phone have no purpose for a marketplace order, so no connector hands them over (ADR-004 SPEC 1, owner ruling, 22 October 2026).

  1. Never kept: buyer email; billing addresses and payment details (except the customer block printed on an issued full invoice); the eBay user id itself, which eBay forbids storing; anything that ties one buyer across orders, marketplaces or sellers.
  2. Used only to ship, for tax and for the seller's service to that order (Amazon AUP): never for marketing, reviews or profiling.
  3. Masked and missing values stay missing. A withheld field is left out, never stored blank or made up, and a later read without it never erases what an earlier read kept (ADR-004 SPEC 1).
  4. Every buyer field carries ADR-001's pii tag (ADR-001 SPEC 5). The tag drives encryption, masking, the logger's drop, anonymisation, export and the AI mask. A build check refuses a column holding buyer data without it.
  5. The destination country and tax territory are Orders' fields, not buyer data (ADR-007 SPEC 5). A postcode a marketplace sends is used to work out the territory and is not kept.

5. Where it lives

  1. Only in the company's rows in its cell, and its label files in object storage, both in the EU.
  2. Ids only everywhere else: queue messages, Durable Object state, the outbox, events, outbound sends and live updates carry ids and statuses (ADR-000 SPEC 10). A screen that needs a name reads it through the API, so the view is logged.
  3. Logs, telemetry and error reports never carry a buyer field: the logger drops any pii value.
  4. URLs never carry buyer data; a search by phone goes in the request body.
  5. Caches: none holds buyer data; Hyperdrive caches nothing.
  6. Emails and push notices name the order number, never the buyer.
  7. The phone client holds buyer data in memory for the screen shown, never in the device's storage. Labels are printed, not saved.
  8. The control database holds no buyer data; the erasure register holds ids and times only.

6. Encryption and keys

  1. In transit: TLS 1.2 or higher on every connection, inside and outside the platform, databases and object storage included (DPP 1.5).
  2. At rest: the database and object storage encrypt everything, backups included.
  3. Field by field: each buyer field is encrypted with AES-256-GCM under the company's data key, with the company id as associated data (ADR-001 SPEC 10). A row read under the wrong company fails to decrypt; a dump or a console query shows ciphertext.
  4. Keys: the company keys are wrapped by a key-encryption key held as a platform secret, rotated yearly and at once on suspicion by re-wrapping.
  5. Label files are encrypted with the company's key before storing, in a bucket of their own with no versioning or soft delete, so deleting one deletes it. This is the one exception to ADR-001's file rule (ADR-001 SPEC 10).
  6. Search: only an exact-match blind index on the phone. Its entry goes with the field.

7. Who can see it

Role Name, address and phone When
Owner, admin, manager Yes Any order that still holds buyer data
Warehouse Yes, in their warehouses only From picking until shipped, and label reprints for 24 hours after (ADR-014)
Accountant Only as printed on issued invoices Never on orders
Staff No Never
  1. Everyone else sees the order masked: number, country and lines.
  2. Every view writes one audit_log entry: opening an order with buyer data, the packing screen, printing or reprinting a label, a buyer search, an export. It names the user, the order, the fields shown (never their values), the screen and the time. Lists show no buyer data and write nothing. The seller sees the entries; audit_log is kept at least a year (ADR-010 SPEC 8).
  3. The operator reaches a company only under a grant: one company, a written reason, at most 8 hours, seen by the seller and ended by them at will. Buyer fields stay encrypted unless the seller's owner or admin switches them on for that grant (ADR-010 SPEC 7).
  4. Developers have no access to production data. The database owner role is used only through the CI migration job, with the reason recorded first and an alert (ADR-001 SPEC 3); even then buyer fields are ciphertext.
  5. Leavers: a person's platform access ends within 24 hours of leaving or changing role, and access is reviewed every quarter.

8. Retention and anonymisation

The order 30 days count from
Delivered, with a delivery date from the carrier or marketplace Delivery (DPP 2.1)
Dispatched, no delivery date known Dispatch, which always comes first, so the limit is never passed
Shipped outside Vervoro The marketplace's shipping time
Cancelled before dispatch The cancellation
On a connection that ended or lost its access The end of the connection, whatever the order's state (DPP 1.7)
Named in a buyer's erasure No wait: at once
  1. An order still to be shipped keeps its address. Delivery is the rule and dispatch the fallback; this is the rule ADR-002 cites (ADR-002).
  2. The due time sits in the cell's due table (ADR-001 SPEC 9). The sweeper, in one transaction per company: clears every pii field on the order and its lines; removes the phone index entry and the eBay hash; marks the order anonymised with the time and reason; deletes its label files.
  3. Once anonymised, never again. A later read or notice that brings the details back stores nothing personal for that order.
  4. Proof: a nightly check counts, per company, orders past their due time still holding buyer data. Anything but zero alerts the operator (runbook).
  5. What survives: the marketplace order id, dates, lines, prices, totals and fees (accounting records); the batch and lot shipped (a recall reaches buyers through the marketplace by order id, ADR-014); the country and tax territory, on the order (VAT); the carrier and service. Not the postcode district or the town: Amazon counts postal codes as personal data.

9. Invoices and export evidence

  1. Invoices follow ADR-011: to a consumer only on request or where the law or marketplace requires, simplified without buyer details wherever allowed (HMRC); a full invoice carries the name and address the law requires.
  2. An issued invoice is kept unchanged for the statutory period (7 years from the end of its month, ADR-002 SPEC 2). After the order is anonymised it is shown only to owners, admins and accountants, each view logged, not searchable by buyer, and archived with its month encrypted under the company's key.
  3. An order delivered outside the UK keeps its carrier, tracking number, dispatch date and the carrier's delivery event (date and country) as export evidence for the statutory period (ADR-011).

10. Buyers' requests

A buyer asks the seller or a marketplace, never Vervoro. Each request becomes a privacy request in the company: who sent it, the orders it names, its due date and when it was done. It holds order ids, never the buyer's details.

Request Arrives from Vervoro does Due

Access The seller; Later: Shopify's customers/data_request A file of the named orders' buyer data, for the seller (section 12) 7 days, inside the law's one month

  1. Finding the orders: by marketplace order id, or by an exact phone number. An eBay deletion names a user, matched by hash (section 16.2).
  2. An erasure keeps issued invoices. The request records that an invoice was kept, and why, so the seller can tell the buyer.
  3. Only owners and admins handle privacy requests (ADR-010 SPEC 4). Procedure: Answer a buyer's data request.

11. Erasure, backups and restores

  1. The live cell: the named orders are anonymised in one transaction, label files deleted, the request marked done.
  2. The erasure register: each completed erasure (order ids and time) is written to control's register and to an append-only log in object storage, both outside the cell and its backups (ADR-001 SPEC 7).
  3. Backups (7 days of history, 30 days of snapshots) still hold the old values, encrypted per field. They are beyond use: nobody reads a backup except to restore. Erasure is complete in backups by day 30 (ADR-001 SPEC 10, ICO).
  4. Every restore replays the register and runs the anonymisation sweep before the company or cell opens to anyone (ADR-001 SPEC 10).
  5. The archive receives orders after 24 months, long after anonymisation (ADR-002); only retained invoices hold buyer details there.
  6. Erasing the company destroys its data key, which makes every remaining copy unreadable (runbook).

12. Exports

  1. A company export (ADR-001 SPEC 10) holds buyer data only for orders that still have it, anonymised orders as they are, issued invoices as issued, and the archive files.
  2. Only an owner or admin makes an export with buyer data; for anyone else the fields are left out. The file is encrypted, offered through a link that expires after 24 hours, deleted after 7 days, and logged with who made it and what it held.
  3. A one-buyer file for an access request holds only the named orders' buyer data, made the same way.

13. Incidents

  1. Alerts to the operator: a canary buyer (one synthetic buyer per cell) viewed, exported or decrypted outside its own test; a user viewing far more buyers than their packing explains, a burst of buyer searches, or an export with buyer data; every operator grant and every use of the owner role; a decrypt failing on a company mismatch, an overdue anonymisation, or a log line that looks like an address or phone; a report from a marketplace, seller, researcher or sub-processor.
  2. The written plan covers preparation, detection, containment, removal, recovery and lessons, is approved by Vervoro's owner, and is reviewed every six months and after a major change (DPP 1.6.2). The operator is the point of contact and Vervoro's owner the deputy. Containment can revoke sessions (runbook), rotate keys and hold every send to a marketplace.
  3. Who is told, counted from when Vervoro becomes aware:
Who When Source
Each affected seller Without undue delay, within 24 hours, so they can decide on the regulator's 72 hours UK GDPR, processor to controller
Amazon, at its security address Within 24 hours, when Amazon data is involved DPP 1.6.3
eBay Within 24 hours, when eBay data is involved Vervoro's rule; eBay asks for immediate notice of a key compromise
Later: Shopify, through partner support Within 24 hours, when shop data is involved Shopify API terms 6.2.10

  1. Vervoro speaks only for itself, never for a marketplace or a seller. Every incident is recorded, including those that need no notice. Procedure: Report a personal-data breach.

15. No real buyer data outside production

  1. Synthetic buyers only in simulators, tests, fixtures and demos: generated names, example.com and .test emails, phone numbers 07700 900000 to 900999, and the postcode ZZ99 9ZZ.
  2. A build check scans fixtures, recordings and seed data and refuses an email, phone or postcode outside those ranges.
  3. Recordings of real marketplace replies (ADR-000 SPEC 9) come from sandboxes and the team's own test accounts, with buyer fields replaced before saving.
  4. A production branch made for a restore holds real data, is reached only by the lifecycle tool, and is deleted within 24 hours (ADR-001).
  5. Staging runs on simulators and synthetic companies only.

16. Per marketplace

16.1 Amazon

Later, with shipping labels (section 0). At launch Vervoro holds no restricted role, and an Amazon order brings no recipient.

  1. The restricted role for direct-to-consumer shipping only, which releases the recipient's name, address and phone on orders the seller ships. Not the tax roles (section 0).
  2. The 2026 orders API releases them by role alone, with no Restricted Data Token. Vervoro asks only for the recipient and gift message, never the buyer's email, and only on seller-shipped orders not yet shipped (ADR-004.2 SPEC 8).
  3. A call that still needs a Restricted Data Token gets one for that order's path and only the elements it needs, held in memory for its life, never stored or logged.
  4. On the end of access, Amazon's notice or the end of participation, everything about that seller from Amazon is deleted within 30 days, except what the law requires to be kept (DPP 1.7). Procedure: Anonymise after a connection ends.
  5. Notices carry a destination postcode; the bridge stores nothing, and the queue message carries ids only.

16.2 eBay

  1. eBay's terms: delete personal data when no longer needed or when asked, never store user ids, destroy within 10 days of leaving the developer programme.
  2. Account deletion notices arrive for every eBay user who closes their account and are answered at once (ADR-004.1 SPEC). A connected seller's is a privacy request; anyone else's is matched.
  3. The match: on import, a keyed hash of the buyer id eBay sends (its username, or its immutable user id) is stored with the order and in buyer_ref(hash, company_id, order_id). A notice is hashed and looked up in each cell with one indexed query through ADR-001's allow-listed function (ADR-001 SPEC 4). A match anonymises that buyer's orders at once. The notice is never kept; the lookup row goes when the order is anonymised.

16.3 Shopify

Later, with ADR-004.3. Level 2 protected customer data for name, address and phone, not email; without approval the fields arrive empty. The three privacy webhooks are checked by signature (401 on a bad one) and handled as section 10 says (ADR-004.3 SPEC 8). Uninstalling ends the connection, so the shop's buyer data goes within 30 days even before shop/redact.

17. The seller's users' sign-in data

Not buyer data: Vervoro is its controller, under its privacy notice. Listed here so one record shows every place personal data lives.

  1. What: each login's email address and name, password hash, authenticator secret, backup codes, passkey public keys, sessions with network address and browser, and password history (ADR-013 SPEC 2). The email address is stored readable, because Better Auth signs people in and mails them by it.
  2. Where: the control database's auth and auth_policy schemas, in the EU. No third-party identity provider owns or acts as the system of record for Vervoro user identities or email addresses. Authentication data remains in Vervoro-controlled infrastructure. Sign-in mail goes through Cloudflare's Email Service, which receives an address only to deliver that email; any other email provider would too (open item in the ADR).
  3. Who: only the sign-in Worker, through the sign-in role. The owner role only in an emergency (runbook). Passwords, codes, secrets and tokens are never logged.
  4. Protection: TLS, storage encryption, authenticator secrets and backup codes also encrypted under the sign-in Worker's secret, every sign-in event in the security log.
  5. Retention: sessions deleted 30 days after they end; a login with no membership deleted after 30 days with its address and name (ADR-010 SPEC 6); control's backups hold it until they expire, within 30 days. A user's own request: Answer a seller's data request.

How to check it was built right

For someone reviewing code an AI wrote. Each line says where to look.

  • One writer: only Buyer data's code writes buyer_ tables and the label bucket; Orders, Fulfilment and Invoicing import only its port.
  • No calls out of the core: Buyer data imports no other module.
  • Tags: every buyer column is declared with pii; the lint runs in CI and fails on an untagged one.
  • Reads: every read of a buyer field goes through one port function that checks role, order state and grant, and writes the audit entry.
  • Ids only: queue, Durable Object, outbox, event and live-update payload types have no buyer field.
  • Logger: the drop of pii values is in the logger, not at call sites.
  • Client: no buyer field is written to local storage, IndexedDB or a cache; no buyer data in a URL.
  • Sweep: one transaction clears fields, the phone index and buyer_ref, marks the order and deletes the label files.
  • Once anonymised: the import path checks the anonymised mark before writing.
  • Restore: every restore path replays the erasure register before the company opens.
  • Bucket: the label bucket has no versioning or soft delete in its configuration.
  • AI: the AI call path masks every pii field.
  • Fixtures: the synthetic-data check runs on every build.
  • Later parts: no Shopify privacy webhook or Amazon tax role at launch.
