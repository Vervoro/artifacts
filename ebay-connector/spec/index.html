1. Connecting

  1. Consent. The seller is sent only to eBay's consent page with Vervoro's scopes: inventory, fulfilment, account and identity (read only), notification subscriptions, cancellations. A scope eBay does not know refuses every seller, so the list changes only after the scope is confirmed on Vervoro's keyset. sell.finances joins the consent once eBay grants it to Vervoro's app (the owner's Growth Check), before the first seller connects, so no seller approves again for fees (owner delegation, 2 November 2026). Today's wording says the scope needs the Growth Check; whether it does is confirmed on Vervoro's keyset before the first seller connects (the owner's to confirm; ADR-016 SPEC 14).
  2. eBay does not sign its redirect; the host's single-use state proves it (ADR-004 SPEC 3).
  3. Who approved. The token reply names no user, so the connector asks eBay's Identity API with the new token. The stable user id is claimed in the external directory. Approving again from the same eBay account renews it.
  4. One account is one eBay site (such as the UK site), which the Trading API calls name.
  5. Tokens. The credential is the refresh token. Its lifetime and each access token's come from eBay's reply. An invalid_grant refusal means the seller removed Vervoro: the account is disconnected. Where eBay's reply names no refresh-token lifetime, 18 months (547 days) (owner delegation, 2 November 2026).

2. Notices

  1. One destination per environment, made by the operator, because it needs the endpoint's verification token, which no hook sees. eBay also needs the application's alert address and checks the endpoint's challenge first. Procedure: Set up eBay notices.
  2. Three topics per seller, subscribed on connect and removed on disconnect: ORDER_CONFIRMATION, ORDER_CANCELLATION_ACTIVITY, ITEM_MARKED_SHIPPED.
  3. Checked with eBay's public key before any company database read; a key id the endpoint does not hold is looked up in control as ADR-004 SPEC 8 says (ruled by delegation, 2 November 2026; confirmed by the owner, 4 November 2026). The queue message holds the topic, the notice id, the seller's user id and the order ids.
  4. What each leads to. A confirmation fetches the order. A cancellation notice fetches it again, and the fetched order's own cancellation state decides; a reminder to answer is ignored. An item marked shipped outside Vervoro fetches the order; Vervoro's own shipments return on the same topic and are not fetched again (ADR-007).

3. Orders

  1. Hourly backup read, 10 minutes while notices look broken; early reads at least one minute apart. The window ends 10 seconds before now.
  2. Cost. Hourly is 24 order calls a day for a quiet seller; every 15 minutes, the first step if a launch gate fails, is 96. Order fetches draw on the same allowance, so the operator checks its room before shortening.
  3. Read backwards. eBay pages orders by offset. The first call reads offset 0; if more pages exist, the read goes from the last page back to offset 0. An order that leaves the window during the read can then only move another onto a page still to come, where it is read twice, and imports are idempotent. Only the final read of offset 0 proves the window complete. A window of n pages costs n + 1 calls.

4. Listings and stock

  1. Every linked listing a SKU is on. A read names, per SKU, the inventory item, each Seller Hub listing by item number, and each variation by item number and its SKU. Only linked listings are written (ADR-005); the host hands their item numbers back on every write and read back. One SKU on several linked listings shows the highest figure any of them shows, so an over-showing listing is always corrected.
Listing kind Call Per call
Inventory item Inventory API, bulk price and quantity update One SKU, up to 25 offers
Seller Hub listing Trading API, ReviseInventoryStatus Up to 4 listings or variations
  1. One failure does not stop the rest: a refused inventory update does not keep the figure from Seller Hub listings, nor one Trading batch from the next, except a refusal of the whole account (a REST 401/403 after the refresh, an account-level Trading error), which stops the batch; nothing is resent listing by listing (owner delegation, 2 November 2026).
  2. Synchronous. A write is applied or refused, never accepted. "Identical quantity" is applied.
  3. A refused batch is resent one listing at a time for the listings its reply does not name as revised, to learn which one eBay refused.
  4. An unknown SKU goes to the Inventory API first. If eBay does not know it there, the Trading API finds its Seller Hub listings, which get no figure and come back to the catalogue to be linked.
  5. A listing that has gone (ended, relisted, SKU removed) makes the connector look the SKU up afresh. A relist eBay declares carries the link; any other is suggested. A SKU on no listing is rejected with eBay's reason.
  6. No compare-and-set. The order watermark is the guard (ADR-008). eBay's 250 revisions per listing per day are counted by ADR-008 SPEC 8.
  7. Read back uses the API that took the write. A listing eBay will not show is looked up afresh by the write's SKU, never its listing key; what it finds goes to Listings; a write without a SKU is read back again (owner delegation, 2 November 2026).
  8. The unknown-write exception. An unknown Trading API write is settled by sending the figure Vervoro wants now again, at the time ADR-008 SPEC 6 sets, because ReviseInventoryStatus sets the quantity and never adds to it, and a read costs the same pool call. An unknown Inventory API write is read back as usual (ADR-004 SPEC 5; owner ruling, 21 October 2026). The resend settles the old write not applied; the newest figure goes next (owner delegation, 2 November 2026).
  9. A variation without a SKU is read and its orders come in by item number and variation id, but it is neither linked nor written. The seller is told to add a SKU in Seller Hub.

5. The Trading pool

  1. ADR-004's pool, with its lanes and reserve (ADR-004 SPEC 7). Accounts whose listings are all inventory items do not use it. At 5,000 a day, a tenth split at 50 calls each serves 10 accounts with Seller Hub listings; more wait in shadow until the Growth Check raises it.
  2. Seller Hub listings are read only when a linked SKU needs them. A Seller Hub listing that shares a SKU otherwise served by the Inventory API is found only when that SKU needs the Trading API.
  3. A daily page cap per account: 50 pages of 200 listings. A read that runs out resumes the next day from where it stopped; nothing is taken as gone from a read that did not run first page to last.
  4. Full catalogue reads prefer the Feed API's daily active listings report (outside the Trading pool), and use the Trading API only for listings new since that report, and only while that costs fewer calls than page reads (ADR-005).
  5. When eBay says the day is spent, the pool is throttled for 15 minutes at a time and the operator is alerted. If the Trading API cannot be read at all, inventory items are still read and written, and each Seller Hub SKU says why it waits. The day spent holds the whole shared pool, for every account on it, through control's hold on the pool's day, 15 minutes at a time (owner delegation, 2 November 2026).
  6. The reset. eBay's daily pools reset at midnight America/Los_Angeles (to be checked against eBay's page when the owner records; owner delegation, 2 November 2026).

6. The out-of-stock option

  1. Asked, never changed. When a read finds Seller Hub listings, the connector reads the seller's selling preferences. While the option is off (eBay's default), every SKU on a Seller Hub listing is left out with a note: turn it on, or eBay ends a listing at 0 and removes a variation. Each SKU left out carries the reason in Listings; the account's notice, with the count left out, shows to every role that reads the account (owner delegation, 2 November 2026).
  2. It blocks going live: a linked listing that cannot be read blocks the shadow check.
  3. Turned off later, sends still go, zero included: selling stock that is gone is worse than an ended listing. The next read shows the note again. The stop and unlink choices on an account whose option is off say that eBay ends a listing sent 0 (owner delegation, 2 November 2026).

7. Cancellations and dispatch

  1. Vervoro sends no cancellation and no answer to a buyer's request (ADR-007 SPEC 12). No Post-Order call is made. The cancellations scope is still asked for, because the cancellation notice needs it. ADR-007 fetches the order again when eBay's 3-day answer window closes.
  2. Dispatch: one Fulfillment API call per box of a shipment confirmed with its own carrier, with its carrier and tracking, through the gate (a box without tracking goes to a person); none for a label bought on eBay (ADR-007 SPEC 20.5, owner ruling, 22 October 2026).

8. Account deletion notices

  1. eBay requires every application to receive account deletion notices for all eBay users. The endpoint answers eBay's challenge with the verification token and checks each notice's signature.
  2. A connected seller: a privacy request with its due date (ADR-004 SPEC 8).
  3. Anyone else: a keyed hash of the user id is looked up in each cell; a buyer found there has their orders anonymised at once (ADR-009 SPEC 16.2). Nothing from the notice is kept.

9. Simulator and pre-launch recordings

The simulator speaks only the calls above: Inventory, Fulfillment, Feed, Notification and Identity APIs, the Trading calls used here, the consent page and token exchange, signed notices, daily usage limits and the out-of-stock preference; with Profit, the Finances API's transactions, their pages and the signature check (section 11). Before launch each call is recorded against the sandbox or a real account (ADR-004 SPEC 14). The recordings include that the order list keeps a stable order for one filter across calls, which the backwards read relies on. getTopics is read on the production keyset: the three topics must be available to Vervoro with the scopes it asks for; any restricted one is requested from eBay before a seller connects.

11. Fees, built with Profit

Built in Profit's phase (ADR-016 SPEC 4.10); until then the connector declares no read-fees (ADR-004 SPEC 1.3).

  1. The call. The Finances API's getTransactions, 1,000 entries a page, over the window Profit's job asks for. A sale's fees per line come from its line items, a refund's credits per line; a fee billed as a separate charge is matched to its order by the order id; label transactions are their order's.
  2. Signed calls. For UK and EU sellers each Finances call is signed with Vervoro's key pair from eBay's Key Management API. The private key is an app secret declared with its rotation (ADR-004 SPEC 2): eBay's key lasts 3 years, and a new pair is made and declared before it ends.
  3. Only the eBay account's owner approves sell.finances. An account approved by a team login reads no fees; its health says "fees need the eBay account owner's approval", and the seller chooses when to approve again.
  4. No buyer field leaves the connector: eBay's transactions name the buyer, and the connector drops it before the host sees an entry (ADR-016 SPEC 12).
  5. Kinds map as ADR-016 SPEC 5 says: the final value fee, its fixed per-order part and regulatory fees are selling fees; the promoted listings (general) ad fee is the line's; cost-per-click charges, the store subscription and other non-sale charges are account charges.

How to check it was built right

  • Two APIs: the write path chooses by what the read learned; inventory items never go through the Trading API.
  • Pool: every Trading call names the shared pool; the page cap is the connector's declaration.
  • Backwards: the order read pages from last to first; the completion mark is set only after offset 0.
  • Exception: the resend path exists only for ReviseInventoryStatus.
  • No settings writes: no SetUserPreferences call anywhere.
  • Notices: signature checked with eBay's key before any company database read; the queue message has no user name or buyer field.
  • No cancellation sent: no Post-Order call in the connector.
  • Later parts: no item-change notice subscription, no listing migration.
